### 生产规则

生产规则定义了一个请求或任务可以执行的操作，例如它执行了多少次查询或模型调用，NestJS Observe 会将每个保留的追踪与此规则进行比对。

有些错误不会抛出异常。重试会两次向卡收费，新的关系会为每个产品加载一行，一个代理循环会调用模型四十次——每个请求都返回 `200`，每个测试都通过，仪表板保持绿色，直到发票、延迟或客户提出异议。

**生产规则**记录了一个请求或任务可以执行的操作——“结账正好调用支付提供者一次”，“产品列表最多运行三次查询”，“没有请求会进行超过五次 LLM 调用”——并且在到达时，每个保留的追踪都会被检查。违反规则的追踪以及它来自的发布版本，在发生的那一刻就清晰可见。当编码代理编写更改时，规则是最廉价的审查方式：用一句话说明生产环境必须保持做什么，在每次部署时都进行检查，而无需任何人重新阅读 diff。

规则无需新的仪器化：它们读取 [SDK](/observability/sdk) 已经记录的 span——你的方法、代理的数据库查询和出站 HTTP span，以及 LLM 调用。它们包含在每个付费计划中，每个项目最多 25 个，在仪表板的 **Activity → Rules** 下。拥有 **Write** 或 **Admin** 权限的成员创建和编辑它们；**Read** 成员可以看到它们。如果计划过期，其规则仍被保留但不再检查，一旦项目再次处于付费计划，检查将恢复。

#### 值得编写的规则

| 必须保持的条件 | 规则 | 违反该规则通常意味着什么 |
| :--- | :--- | :--- |
| 支付只进行一次 | `POST /checkout/:orderId/pay` 恰好调用 `POST api.stripe.com` 一次 | 重试或重复的处理器两次收费，或停止收费的重构 |
| 产品列表没有 N+1 | `GET /products` 最多运行 `pg SELECT products` 3 次 | 关系现在为每行加载一次 |
| 端点运行成本保持低廉 | 每个请求最多进行 5 次 LLM 调用 | 持续调用模型的工具或代理循环 |
| 管理员更改被审计 | `PATCH /admin/users/:id` 至少调用 `AuditLogService.record` 一次 | 跳过审计写入的新代码路径 |
| 任务发送一个摘要 | `send-digest` 任务恰好调用 `POST api.postmarkapp.com` 一次 | 部分失败后重试的任务，向所有人发送两次邮件 |

最好的规则来自于你刚刚进行的更改：它必须保持做什么？在你知道答案时编写的规则，即使 diff 被遗忘很久后也能约束生产环境。

#### 规则的含义

规则以一句话的形式存在，仪表板的表单在编写时就显示该句子：

- **操作**：一个路由和方法（`POST /checkout/:orderId/pay`），一个按名称命名的任务，或每个请求或每个任务。尚未被服务的路由是没问题的：直到收到其保留的追踪，规则显示为 **Unchecked**。
- **每次执行计数的内容**：
  - **对类或方法的调用**：一个提供者方法，例如 `PaymentsService.charge`，或一个驱动语句，例如 `pg SELECT orders`，命名方式与 **Services** 视图中的名称一致。
  - **对主机的出站 HTTP 调用**：`api.stripe.com`，可选配一个方法。未指定端口的主机将在任何端口上匹配。
  - **LLM 调用**：每次模型调用，或一个提供者（OpenAI、Anthropic、Azure OpenAI 等，或你配置的网关）。
- **约束**：每次执行的次数是恰好、最多还是至少。

上界（恰好、最多）由每次执行保持，包括失败的执行。下界（恰好、至少）仅由成功的执行保持——无错误，状态低于 `400`——因为中途失败的请求没有机会进行调用。

只计算 SDK 本身记录的 span；你用 [`TracerService`](/observability/manual-instrumentation) 手动打开的 span 不计算。当一个方法进行超过 20 次相同调用时，SDK 会保留最慢的几个并将其余的折叠成单个 span（参见 [configuration reference](/observability/sdk#full-configuration-reference) 中的 `spanCollapse`）。规则会按实际数量计算折叠的调用，因此五十次 N+1 查询被计为五十次。

#### 从证据出发编写规则

你可以在 **Activity → Rules** 下从零开始编写规则，但有两种快捷方式可以从提示该规则的遥测数据开始：

- 在 **Releases** 页面将规则 **固定**。每个发布版本添加的、或现在更频繁执行的查询、出站调用或方法都会打开包含该调用的表单，并从该发布版本的数字中获取起始边界。路由由您选择，因为发布版本的数字是每个请求的平均值。
- 在追踪的瀑布图中 **用规则守卫**。SDK 折叠成单个 span 的调用序列（N+1 的形状）会打开一个预填了该追踪自身路由或任务、调用以及最多 3 的边界的表单。

在您点击 **创建** 之前，两者都不会保存任何内容。

#### 检查已保留的追踪

规则由追踪工作进程检查其保留的追踪，从规则保存的那一刻起——绝不检查更早的追踪。编辑和切换将在大约 30 秒内生效。这对数字意味着：

- **违规是确定的。** 这是一个已经发生的执行，其追踪仅一步之遥。
- **规则的持有是证据，而非证明。** 当 [spend controls](/observability/overview#subscribing) 样本 span、服务器错误和慢于一秒的追踪始终被保留，其余的按保留率处理时，被检查的追踪倾向于慢的和失败的。
- **计数是检查的追踪，而非请求。** 被检查的追踪的份额不等于请求的份额。
- **稀疏窗口说明了这一点。** 在保留的追踪少于平时的某一天，规则仅在这些追踪上进行检查，并且规则页面会在数字上方发出警告。

每条规则都会显示您选择的窗口（最近 24 小时或最近 7 天）的状态：

| 状态    | 含义                                                           |
| --------- | ----------------------------------------------------------------- |
| Violated  | 在该窗口内，至少有一个被检查的追踪违反了规则           |
| Holding   | 已检查，且从未违反                                         |
| Unchecked | 未到达该操作的任何保留追踪，因此未判断规则           |
| Disabled  | 已关闭；计数来自之前                          |

每条规则的页面会列出违反它的最新追踪，每个追踪都会打开其瀑布图，并显示每个发布版本的检查和违规情况，以及每个版本开始和停止违反的时间——哪个发布版本违反了规则通常是第一个问题。

#### 规则警报

在创建规则时开启 **当此规则违规时通知我**，届时会创建一个警报：每小时超过 0 次违规，严重性为 High，在应用内和通过电子邮件。它在第一个违规追踪上触发，并在最后一个违规追踪后一小时内解决，每次事件只触发一次，而不是每次请求都触发一次。任何 [alert rule](/observability/dashboard#alerts) 也可以监控 **生产规则违规** 指标，可以针对单个规则或项目/应用程序中的每条规则。

#### 来自编码代理

在 [MCP server](/observability/mcp-server) 上，在每个付费计划中，`create_production_rule` 允许发布变更的代理固定生产环境必须继续执行的操作，同时它仍然知道，并且 `list_rule_violations` 读取与仪表板显示相同的报告。编辑和删除规则仍保留在仪表板中。

代理不需要被告知规则的存在。服务器在客户端连接时发送的指令将 `create_production_rule` 命名为变更发布后需要查找的写入，`get_context_pack` 列出项目的规则以及每个规则在过去一天的持有情况，当一个发布版本添加了一个出站调用或一个陈述，或更频繁地执行一个陈述时，`get_release_verdict` 最后会包含一行说明哪些值得固定。

> info **提示** 规则仅读取 SDK 已发送的追踪。仪表板和代理都不能使用规则来扩大 SDK 的捕获范围。
