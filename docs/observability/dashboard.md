### 仪表盘

一旦应用程序被仪器化并发送数据，其项目仪表盘会自动填充，无需编写查询或构建仪表盘。本章介绍每个视图显示的内容、视图之间的关系，以及基于遥测构建的功能（发布判决、状态页面、警报、SLO、问题和代理交接）是如何协同工作的。完整参考请参阅 [NestJS Observe documentation](https://www.observe.nestjs.com/documentation 'NestJS Observe documentation')。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/dashboard.webp" alt="Project dashboard" /></figure>

> info **提示** 下述描述的每个视图都可以在 [live demo](https://www.observe-demo.nestjs.com/dashboard 'NestJS Observe live demo') 中点击穿梭，该视图使用来自繁忙服务的生成数据集运行仪表盘：真实的请求量、带有瀑布图的追踪、错误、任务和警报。它不需要账户，完全在您的浏览器中运行。

#### 视图的嵌套方式

几乎所有遥测视图都属于三个级别之一，您通过点击穿梭在它们之间移动：

1. **分析 (Analytics)** - 列表视图。在选定时间窗口内，您的应用程序报告的每个路由、任务、跨度或指标的聚合：吞吐量、延迟、失败率。您在这里发现异常。
2. **操作 (Operation)** - 一个路由（`GET /orders/:id`），一个任务名称，一个跨度名称。随时间变化的相同数字，以及其背后的单个执行列表。您在这里确认问题的形态：恒定还是尖峰，是普遍存在还是仅在一个发布中出现。
3. **执行 (Execution)** - 单个请求、单个任务运行、单个跨度调用。其确切持续时间、状态、用户、标签、引发的错误、其执行的所有操作的瀑布图以及它写入的日志。您在这里进行诊断。

聚合告诉您**存在**问题以及问题的严重程度；单个执行告诉您**原因**。每个视图共享一个控制栏（时间范围和可选的应用程序过滤器），页面上的所有内容都遵循此控制栏。

#### 遥测视图

| 视图 | 显示内容 |
| :--- | :--- |
| **请求 (Requests)** | 按操作细分的每个 HTTP、GraphQL、gRPC、微服务和 WebSocket 网关请求。请求详情页将调用与路由自身的基线（“慢于 95% 的调用”）进行比较，并在进程遇到困难时，说明主机压力使该操作减慢了多少。 |
| **服务 (Services)** | 每个 NestJS **类和方法**的耗时，分为自身时间（减去所有已等待时间）和总时间。仅显示已仪器化的类，因此简短列表意味着覆盖率低，而非流量低。 |
| **错误 (Errors)** | 每个未处理的错误，按操作分组，失败信息位于页面顶部：类、消息、堆栈跟踪和源代码。**按缺陷分组**开关将具有相同类和堆栈形状的发生情况合并为一个指纹分组，显示首次/最后出现时间和引入该错误的发布。参见 [Error monitoring](https://docs.nestjs.com/observability/error-monitoring)。 |
| **任务 (Jobs)** | 后台工作——队列消费者、定时任务——包含队列等待时间、尝试次数和失败原因，以及持续时间和失败率。 |
| **跨度 (Spans)** | 对代码使用 [`TracerService.createSpan()`](/observability/manual-instrumentation) 创建的自定义跨度的分析，跨越调用它们的每个路由——“`OrdersService.recalculate` 在所有地方有多慢”，而不是“这个端点有多慢”。SDK 记录的跨度则在每个执行的瀑布图中读取。 |
| **追踪 (Traces)** | 针对一个追踪 ID 的瀑布图，跨越共享该 ID 的每个服务——参见 [Distributed tracing](/observability/distributed-tracing)。 |
| **用户 (Users)** | 当配置了 `getUserId` 时，按用户活动统计：每个用户的失败率、按执行的操作分组的调用、每个操作的重放以及它们之间的路径。**按客户分组**开关按电子邮件域名汇总身份。 |
| **自定义 (Custom)** | 通过 [`TracerService`](/observability/manual-instrumentation#自定义指标) 报告的计数器、仪表和摘要，按指标名称和标签分组。 |
| **发布 (Releases)** | 将每个 `serviceVersion` 与其前一个版本进行比较——错误率、延迟和吞吐量并列显示——并给出关于部署是使情况恶化还是改变代码行为的判决。参见 [Releases and their verdicts](/observability/dashboard#releases-and-their-verdicts)。 |
| **日志 (Logs)** | 您的服务记录的所有内容（开启 `forwardLogs`），与它们运行的追踪相关联。在执行页面上，每行日志都放置在追踪的时钟上，紧邻正在运行的跨度。 |
| **分析器 (Profiler)** | 每个应用程序的 CPU、内存、事件循环延迟和利用率以及垃圾回收情况，当应用程序在多个节点上运行时，提供每个实例的比较。点击内存或事件循环延迟图上的尖峰，查看当时运行了哪些操作，并按偏离基线的程度排序。 |
| **规则 (Rules)** | [Production rules](/observability/production-rules)：请求或任务可能执行的操作，针对每个保留的追踪进行检查，并显示违反每条规则的追踪以及它们来自的发布。付费计划。 |

#### 查询、出站调用和捕获的请求

在追踪的瀑布图中，数据库查询或出站 HTTP 请求是其发起方法的单独一行：一个图标、操作（`SELECT orders`, `POST api.stripe.com`）以及旁边的语句或 URL，无需悬停即可看到。该行的箭头会展开完整的语句，按子句布局，并高亮显示其占位符和一个复制按钮。值永远不会显示，因为代理在发送任何内容之前会移除它们。下方的跨度表仅列出您的应用程序方法；代理的查询跨度被排除在外，其时间计入调用方法的自身时间，因此该表仍然回答“我的哪些方法花费了时间”。**服务**页面遵循相同的规则：驱动程序（`pg`, `mysql2`, `mongodb`, `http`）不作为类列出，查询的等待时间计入运行它的方法的自身时间。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/sql.webp" alt="A query opened in the waterfall" /></figure>

当代理保留了请求自身的输入（因为它失败了，或者运行超过了您配置的 [`slowerThanMs`](/observability/sdk#capturing-failed-and-slow-requests) 阈值）时，请求的**详情**卡片有两个额外的折叠行：*请求头*和*请求体*。没有捕获内容的请求没有此类行。

#### 服务图

项目的**活动 → 映射**页面显示了其应用程序、队列和数据库之间如何相互通信。应用程序和队列按调用顺序从左到右运行，它们所依赖的数据库和外部服务则悬挂在下方。线条的粗细和沿线的流量速度显示了流量量。柔和的红色表示错误率高于 1%，完全红色表示高于 5%，青色表示健康。将鼠标悬停在任何节点上以隔离其接触的对象，然后点击它查看其数值：对于数据库，是花费时间的语句；对于应用程序，是它调用的以及调用它的，并附有其请求的链接。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/map.webp" alt="Service map" /></figure>

该图无需配置，不收集任何新数据。数据库和外部主机来自代理的 [query and outbound-HTTP spans](/observability/sdk#database-queries-and-outbound-http)，队列来自应用程序处理的任务，应用程序之间的虚线来自共享一个 [trace id](/observability/distributed-tracing) 的执行。每个应用程序针对每个驱动程序获得一个数据库节点，因此两个在 Postgres 上的服务通常显示为两个数据库，因为网络上没有任何信息表明它们共享一个。相比之下，外部主机是一个由每个调用者共享的单个节点，每个应用程序最多有八个最繁忙的。

一个完全没有线条的应用程序几乎总是运行早于 `0.3.0` 的 SDK，该 SDK 不报告查询或出站调用。

> info **提示** 应用程序之间的链接是从最近的请求推断出来的，而不是在整个窗口内计数。将虚线视为“此调用彼”，而不是精确的总数。

#### 发布及其裁决

**发布**视图列出了您的应用程序报告的每一个 `serviceVersion`。打开其中一个，它会以一个**裁决**开头：部署是否使情况恶化，以及自那时以来是否有任何行为不同，用一个词和一句话概括。

- **回归** - 服务器错误 (5xx) 在发布边界处增加了超过噪声的量。
- **变更** - 服务器错误没有增加，但该发布做了新的事情：首次出现的错误组、变得安静的路由，或代码调用内容的改变。
- **干净** - 没有这些。句子说明了比较了什么，因此对过少遥测数据的干净裁决不应被解读为更多。
- **数据不足** - 两侧请求太少，无法判断。

在裁决下方是其依据的证据：首次在发布中出现的错误组、在边界前稳定提供服务的路由而在边界后没有（请求从不采样，因此变得安静的路由确实停止了）、出站主机、查询形状以及只有边界一侧调用的方法，以及需要首先阅读的注意事项——采样跨度，或其数值描述了不同版本的滚动部署。

**代码中发生的变化** 接着列出了行为变化超过噪声的查询、出站调用和方法：**新增**或**移除**，每个请求中被调用次数增加了 **44×** 的语句——新的 N+1 通常就是这样显示的，远在 p95 移动之前——或自身时间慢了 **7.6×** 的方法。发布添加的或现在调用频率更高的调用，提供**作为规则固定**，启动一个 [production rule](/observability/production-rules)，命名下一个需要打破的发布。这些都没有收集任何额外数据：它们读取与仪表板其余部分相同的请求行和每方法遥测数据。代理在 [MCP server](/observability/mcp-server) 内获得相同的裁决，使用 `get_release_verdict`。

#### 状态页面

在 Pro 及以上版本中，应用程序可以拥有一个公共的**状态页面**：该页面显示了您的套餐有效期内每天的可用性和 p95 响应时间，地址可提供给使用者。在**应用程序**列表中，点击应用程序行上的广播图标，或从其菜单中选择**状态页面**并开启——拥有写入或管理员权限即可。在同一位置撤销即可；再次发布将恢复相同的地址。**显示响应时间**默认开启；关闭后，页面仅显示可用性。

<figure><img src="https://www.observe.nestjs.com/docs/applications/status-page.webp" alt="Status page" /></figure>

可用性是指未因服务器错误（5xx）而失败的**请求**的份额；客户端错误（4xx）不计入其中。一天若达到 99.5% 或更高，则为**正常运行**；若为 95% 则显示**高错误**；低于此则显示**主要错误**；请求少于 20 的一天将显示其数值而无状态。该页面绝不显示应用程序获得的流量，也不会因任何 Observe 观察到的情况而判定应用程序宕机：未记录任何**请求**的一天会明确显示这一点，而超额收集暂停的一天则标记为部分记录并排除在统计数据之外。页面每分钟刷新一次，并且不会被搜索引擎收录。

#### 将故障转交给编码代理

阅读追踪可以告诉您发生了什么。下一步总是相同的：找到相应的代码并修改它。**复制代理提示**按钮将此交接在一键完成。它将整个页面复制为一个自包含的 markdown 提示，可直接粘贴到 Claude Code、Cursor 或任何已打开您代码仓库的工具中。

该按钮仅出现在有需要调查内容的地方：失败的或运行时间慢于其同行 95% 的**请求**或**任务**，或包含错误的追踪。该提示携带了任务框架、操作**执行上下文**、带有修剪后的堆栈追踪和源行（路径相对于您的项目根目录重写，因此是 `src/orders/orders.service.ts:35` 而不是 `/var/app/current/dist/orders/orders.service.js:35`）的错误，调用与操作平均值和 p95 的比较、按自时间排序的前置跨度、最多 40 行优先选择错误日志，以及要求代理从代码中解释根本原因并以带有测试的 diff 形式提出修复的结束指令。

<figure><img src="https://www.observe.nestjs.com/docs/telemetry/copy-agent-prompt.webp" alt="Copy agent prompt" /></figure>

对于需要持续提问的代理（深入其日志追踪，检查错误是否仍在触发），请将其连接到 [MCP server](/observability/mcp-server)。

#### 警报

警报会在您的遥测数据跨越您关心的阈值时通知您，这样您就不会从客户那里得知问题。一个规则会监控来自以下家族中的一个指标：

| 家族 | 指标 | 作用域 |
| :--- | :--- | :--- |
| Request | 错误率、p95 延迟、平均延迟、吞吐量 | 一个应用程序，以及可选的一个路由 + 方法 |
| Job | 任务失败率、任务吞吐量、p95 队列等待时间 | 一个应用程序，以及可选的一个任务名称 + 队列 |
| Absence | 遥测静默、任务静默 | 一个应用程序，或一个任务名称 + 队列 |
| Logs | 匹配的日志行 | 一个模式，以及可选的级别 + 日志记录器**执行上下文** |
| Errors | 新的错误组 | 一个应用程序，或整个项目 |
| Runtime | 事件循环延迟、CPU 使用率、内存使用率 | 一个应用程序（按进程采样） |
| Custom | 您的应用程序报告的任何自定义指标 | 一个指标名称，以及可选的一个标签 |
| SLO | SLO 消耗率 | SLO 本身 |
| Production rules | 生产规则违规 | 一个规则，或项目或应用程序中的所有规则 |

**错误率**仅计算服务器错误（5xx）。4xx 是客户端的错误——爬虫的 404、会话过期的 401、验证失败——因此它永远不会触发错误率规则，尽管它仍会显示在 Requests 和 Errors 视图中。

每个规则以两种模式之一运行：**固定阈值**（“错误率高于 5%”），或**异常检测**，当指标偏离其自身近期基线超过您设定的敏感度时触发。异常模式通常是运行时指标的更好选择：一个适合某个**服务**的固定 CPU 阈值对下一个**服务**就不适用了，但“与自身近期基线不同”适用于两者。

两个家族直接依赖于 SDK 仪器化：

- **缺失检测**。一个**遥测静默**规则会监控 SDK 的 `runtimeMetrics` 采样器即使在应用程序空闲时也发出的运行时心跳，并在静默时间超过您设定的容忍度（2 分钟到 7 天）后触发。一个**任务静默**规则对一个命名的**任务**执行相同操作，例如未运行的定时任务。相同的机制为您提供了无需外部探针的轻量级正常运行时间监控和定时任务监控。从未报告任何内容的**作用域**不会触发：“尚未集成”不等于“宕机”。
- **日志模式警报**计算窗口内包含子字符串的日志行（“当 `payment declined` 在 15 分钟内出现超过 10 次时通知我”），并要求 `forwardLogs` 开启。

规则可以通过 **email**、**Slack**（传入 Webhook）、通用 **webhook**、**应用内**通知或**创建问题**（预填充规则的严重性和作用域）进行通知。规则可以携带用于静默时段的重复静默计划，并且每次状态转换（OK → Firing → Resolved）都会记录带有每个渠道的交付状态。

<figure><img src="https://www.observe.nestjs.com/docs/alerts/create-alert.webp" alt="Create alert" /></figure>

**启动警报**。付费计划并非空启动。当计划开始时，以及每当将应用程序添加到其付费项目中时，每个应用程序都会获得两条规则：一条通过邮件通知账户所有者，另一条在应用内显示：

- **异常错误率** - 基于 15 分钟内错误率的异常规则。它不会在基线过薄无法判断时触发，并等待 20 个请求和比应用程序通常更多的 5 个服务器错误，因此单个失败的请求不会触发警报。
- **静默** - 一个具有 15 分钟容忍度的遥测静默规则，在应用程序连续一周报告后添加，因此笔记本电脑夜间休眠不会通知任何人。

它们是普通的规则：可以编辑其渠道或阈值、关闭它们或删除它们。在没有警报规则的 Free 计划中，系统会为您监控这两项：检查全天候运行的应用程序的异常错误率和静默情况，每个账户每 30 天最多收到一封警报邮件。

**新错误**。*新错误分组*规则在观察到从未见过的错误时触发。它只计算未处理的失败：首次出现时返回 5xx 的分组，或在没有 HTTP 状态码的入口点（RPC 处理程序、网关消息）失败的分组。您的代码有意抛出的错误，例如 `NotFoundException` 或验证失败，仍然会出现在错误视图中，但不会被计为新 Bug。每个计划，包括 Free，都内置了**新错误邮件**，无需创建规则：每个项目最多每天一封邮件，列出新错误。每个人可以在**设置 → 新错误邮件**下关闭此功能。

#### SLO

SLO 将“错误率高于 5%”转化为“我们承诺 99.9%，但预算消耗得太快了”。它们是基于您已收集的遥测数据的目标，因此无需新的仪器化。SLO 由三个分层概念构建：

- **SLI (服务等级指标)**：在时间窗口内良好事件与总事件的比率，用于衡量可用性（无未处理错误的请求）、延迟（低于您设定的阈值的请求）或任务成功率。
- **目标**：SLI 加上在 7、14、28 或 30 天滚动合规窗口内的目标百分比（90-99.999%）。
- **错误预算**：您偏离目标的余地（`1 − target`），以及**消耗率**，即预算消耗的速度。1.0 的消耗率表示恰好按计划消耗；14.4 表示 28 天的预算在大约两天内就会用完。

SLO 也可以在它所覆盖的处理程序旁边声明，使用 [`@Objective()`](/observability/sdk#declaring-objectives-in-code)，因此它会与路由一起被审查和版本控制。消耗率警报是指向 SLO 而不是原始指标的常规警报规则。典型的起始点是快速消耗规则（1 小时窗口，14.4×）、慢速消耗规则（6 小时，6×）和涓流规则（3 天，1×）。合规窗口不能超过您的计划保留遥测数据的时长。

#### 问题

问题是轻量级的、项目作用域的跟踪，用于处理来自遥测数据的后续工作，例如值得修复的重复错误或需要调查的延迟回归。您可以从任何执行页面手动创建它们，将错误分组提升为问题，或让触发的警报自动创建问题。一个问题链接到其来源的请求、错误、任务或跟踪，因此稍后打开它的人不仅有描述，还有上下文中的遥测数据。

每个链接到遥测的问题都会以其**事件记录**打开：关于什么（错误类、路由或任务以及触发它的警报规则）、何时开始和结束、它包含的发布版本、影响了谁（用户以及其电子邮件域背后的客户公司）以及修复它的发布版本，所有这些都在一个时间线中。**复制摘要**将整个记录作为纯文本复制到剪贴板，用于事后分析、状态更新或给客户的备注。

<figure><img src="https://www.observe.nestjs.com/docs/issues/incident-record.webp" alt="Incident record" /></figure>

从错误分组提升的问题还会回答**是否有发布修复了这个问题？** 选择一个发布版本，答案将基于该发布版本的请求、错误失败的路由，以及它在此之前失败的频率来判断：**已修复**、**未修复**、**信息不足**或**数据不足**。它还会显示该发布版本中首次出现的错误分组在相同路由上的情况，因为仅移动错误抛出位置的修复会赋予它新的指纹。计数来自请求行，请求行永不采样，因此只要该发布版本服务了足够多的这些路由，答案就存在。代理使用 `verify_fix` 提出相同的问题。

当您将问题标记为已解决，并且它指定了可衡量的对象（操作、警报规则的作用域）时，仪表板会监控该操作的遥测数据与其事件前基线进行比较，并告诉您修复是否有效。它将问题移动到**验证中**，然后要么自动关闭它，要么将其移回**打开**状态，并附上导致其失效的读数。在 7 天内没有确凿结论的情况下——通常是流量不足以判断——它会显示**未验证**，然后您手动关闭该问题。如果您指定了修复所在的发布版本（您的 `serviceVersion`），验证将等待该发布版本出现在遥测数据中。

#### 通过仪表板的排查路径

视图设计为按顺序使用。典型的排查流程如下：

1. 触发警报，或 **请求** 图表显示 p95 攀升。
2. 按持续时间或失败率对路由列表进行排序，以找到哪个操作发生了变化。
3. 打开该操作。它是恒定的还是尖峰式的？是否在部署时开始的？检查 **发布**，以及该发布的判决。
4. 从分布的尾部打开单个执行，例如，基线卡调用了“比 95% 的调用慢”的那个。
5. 阅读 **瀑布图**：哪个跨度持有自耗时间？
6. 如果失败，阅读 **错误卡** - 堆栈跟踪和抛出周围的源行。
7. 检查该跟踪的 **日志**，悬停行以将其与跨度对齐。
8. **复制代理提示**，并将全部内容交给编码代理，或者打开一个链接到该执行的 **问题**，以便接手的人从你停止的地方开始。

当您宁愿提问而不是点击浏览视图时，该路径也可通过 [MCP server](/observability/mcp-server) 对代理开放，每一步使用一个工具。
